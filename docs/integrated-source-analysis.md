## 1. 분석 범위와 주소·행의 단위

이 문서는 PC-88판 바리스 II의 Disk A–G에서 부팅·메뉴, 시스템 오류 문구, 이벤트 대사, 엔딩·크레딧, 음악·경고·당첨 화면, 글리프 ROM과 타이틀·전투 그림까지 확인된 분석 결과를 연결한다. 실행 로그, 원본 바이트 덤프, 날짜별 번역·패치표, 사용자 실행 보고는 서로 다른 증거로 읽는다.

`RAM 주소`는 실행 중 메모리의 주소이고 `raw 오프셋`은 D88 파일의 바이트 위치다. 둘은 동일한 주소 체계가 아니다. 이 문서의 sector별 raw 범위는 16바이트 D88 섹터 헤더를 제외한 데이터 바이트를 가리킨다. 한 섹터의 데이터는 `0x400`바이트이며, 섹터를 건너는 RAM 연속 영역은 raw 파일에서는 헤더만큼 간격이 생긴다.

표의 행 수도 같은 단위가 아니다. 실행 행에는 제어 토큰과 서브스트림이 들어갈 수 있고, 번역 위치는 표시 문자 슬롯만 센다. payload 바이트 수는 종료·호출 제어를 포함할 수 있으며, 실제 변경 바이트 수와도 다르다. 본문은 이 수치를 서로 바꿔 읽지 않도록 각 판본의 기준과 주소를 함께 적는다.

## 2. 기록 판본 구분

자료는 작성 시점과 확인 방법에 따라 세 층으로 나뉜다. 원본 실행 기록은 일본어 토큰이 실제로 읽힌 순서와 RAM 상태를 추적한다. 날짜별 번역표·패치 기록은 특정 시점의 문안, 토큰, 주소와 수정 bytes를 정리한다. 2026년 9월 저장 참고판은 그 뒤 저장된 편집 상태를 비교하는 데만 사용한다. 세 층의 행을 같은 순번으로 간주하거나, 늦게 저장된 상태를 과거 실행의 증거로 소급하지 않는다.

이 문서에서 **저장 참고판**은 9월에 확인한 후속 편집 상태를 뜻한다. 직접 패치표의 raw 주소와 교체 bytes를 대신하지 않으며, 그 상태의 데이터가 게임에서 실행됐음을 증명하지도 않는다. 아래 비교표는 작업표와 저장 참고판의 차이를 설명할 때에만 이 기준을 쓴다.

KANJI1 글리프 배정도 같은 구분이 필요하다. 작업 기록에는 6월 19일 123개, 7월 14일 361개, 8월 중순 이후 558개 배정 상태가 차례로 나온다. ROM 크기는 모두 131,072바이트지만 글리프 번호와 바이트 배치는 달라질 수 있다. 따라서 한 날짜의 문자 토큰과 다른 날짜의 ROM 접근 주소를 섞어 해석하지 않는다.

## 3. 영역별 기술 모델

### 3.1. Disk B·C 시스템 문구

8월 12일 Disk B 최종 패치 기록에 따르면 W1–W3는 raw `0xA80–0xB04`, 저장·시작·메뉴·W4는 `0x514E0–0x516A1`에 있고 R/X는 별도 블록으로 정리돼 있다. 물리 복사본 합계는 1,711→1,615바이트, 즉 96바이트 감소다. R1/R3와 R2/X1/X2는 A/B 쪽에서 공유 포인터를 사용하지만 R4/R5의 포인터는 복사본마다 별도다. 따라서 같은 일본어 문구를 찾았다는 이유만으로 A/B의 서로 다른 raw 영역을 하나로 합치면 안 된다. 용도 미확정인 raw `0x36C90–0x36C98`의 `がいたぜ[00]`는 패치에서 보존한다.

B의 W1 오류 문자 슬롯은 raw `0x0AA5`/RAM `0675`, W2 오류 문자는 raw `0x0AC0`/RAM `0690`, W2 드라이브 숫자는 원래 raw `0x0AD4`/RAM `06A4`다. W2 문장을 2바이트 줄이면서 번호가 RAM `06A2`로 이동하므로 raw `0x0A6A`의 store 피연산자가 `32 A4 06→32 A2 06`으로 바뀐다. 번호 자체는 실행 중 쓰는 값으로 취급한다. X1/X2의 사용자 선택 짧은 번역은 158바이트 용량 중 156바이트를 쓰고 2바이트를 00으로 채운다. 최종 적용과 사용자 확인은 기록돼 있으나, **후속 편집에서** R/X 포인터를 다시 이동할 때에는 에뮬레이터 재검증이 필요하다고 후속 편집의 조건으로 따로 남겼다. 이 후속 변경 조건을 현 패치 미완료로 바꾸지 않는다.

8월 11일 Disk C 최종 패치 기록은 C1 `0x0A80–0x0B04`, C2 `0x144A–0x14DB`의 시스템 문구 여섯 개를 279→249바이트로 줄였다고 기록한다. C1은 53 유지, 42→40, 38→36바이트이고 C2는 33 유지, 76→58, 37→29바이트다. 빈 2·2·18·8바이트는 00이다. C1의 동적 오류 문자 두 슬롯은 보존하고, C1-2의 번호 슬롯 `0x0AD4`/RAM `06A4`를 `0x0AD2`/RAM `06A2`로 이동해 B와 같은 raw `0x0A6A` store 피연산자 `32 A2 06`을 기록한다. C2에는 추가 동적 store가 확인되지 않았다. 신규 글리프 팅·킵·셋의 토큰은 각각 `E8 7B`, `E8 7C`, `E8 7D`이고 KANJI1 ROM 접근 주소는 `13F80`, `13FA0`, `13FC0`이다. 크기·해시·00 채움의 정적 대조와 사용자 QUASI88 실행 성공이 모두 기록돼 있다.

### 3.2. Disk D의 저주소 화면과 Disk F 오류 문구

7월 9일 저주소 화면 분석의 핵심은 Disk D 이벤트 D2F2–E608 후에 보이는 DISK B ERROR/RETURN 화면의 **출처**다. 이 화면은 D 이벤트 스트림 자체가 아니라 상주 RAM `0600–06FF`에서 출력되고, 문서가 추적한 원본 우선 패치 위치는 Disk A raw `0x03A50–0x03B4F`다. `0629` 출력 루틴, `DE=065F`, `06BE` RETURN, `063A` 포트 대기와 `0684` 문자 store의 관계를 제시한다. 동적 문자는 RAM `0684`의 오류 디스크, `069F`의 교체 안내, `06B3`의 드라이브 숫자다. 표 3–5는 A 저주소 화면, B/C `0A80–0B04`의 독립 사본, F의 별도 포맷, G의 A형 사본을 구분한다. D/E에 같은 저주소 블록이 없다는 결론은 주소 출처에 관한 것이며 이 7월 문서 자체가 최종 D 패치를 증명하지는 않는다.

8월 11일 Disk F 오류 문구 최종표의 F1은 raw `0x0A3B–0x0A8F` 85바이트, F2는 `0x0A90–0x0AE0` 81바이트다. 같은 데이터 섹터에서 인접해도 두 고정 용량을 합친 166바이트 한 공간으로 재배치할 수 없다. 앞의 `0x0A20–0x0A2F`는 섹터 헤더다. `0D`와 `00`은 줄바꿈·종료 제어이며 `81 96`, `81 40`, `81 41`, `81 42` 등은 표시 문자다. 최종 F1은 85바이트를 채우고 F2는 75바이트를 사용해 `0x0ADB–0x0AE0`의 6바이트를 00으로 채운다. F2의 동적 디스크 A 두 번째 바이트는 raw `0x0A9B`/RAM `066B`이며 코드 `05F5`의 `LD (066B),A`가 쓴다. 반면 DRIVE 2의 숫자 raw `0x0AAE`는 고정 문자이고 RAM `0374`의 임시 store와 구별한다. 출력은 `05FB`의 `LD DE,0660`에서 시작한다. 문서는 최종 415,840바이트 D88 해시와 사용자 런타임 성공을 기록하며, 이 범위는 새 글리프 없이 기존 배정을 쓴다.

### 3.3. Act 1–5: 원본 실행표, 번역 워크북, 패치 기준의 관계

**Act 1 (Disk D).** 7월 10일 일본어 작업표는 20블록·81개 표시 구간·2,266개 문자 위치를 구분한다. 7월 13일 런타임 표는 2,812행이며 `D99F=43` 제어행을 포함한다. 그 제어행을 넣기 전의 2,811행 초안에는 표제·분할 제목이 일부 남아 있었다. 7월 14일 패치 기준은 2,812행(본류 2,454·서브스트림 358)이고, 제어행 546개를 포함한다. 본류는 `D2F2–E608`, 공통 서브스트림은 `E616–E7A3`이며 그 사이 `E609–E615` 13바이트는 보존한다. 2,266개 문자 위치는 한글 1,693·공백 437·문장부호 136이고, 중복 주소 761개는 같은 값을 쓴다. 결과 이미지의 실제 SHA-256은 같은 날짜에 보고된 예상값과 일치하지만, 이는 보고된 이미지의 식별 확인이지 일본어 원본에 처음부터 다시 적용한 재현은 아니다. 9월 저장 참고판은 2,811행·2,265문자 위치·`E606=26`이며 `D99F=81 49`로 분류한다. 서로 다른 판본의 행 차이를 게임 제어행의 누락으로 단정하지 않는다.

**Act 2 (Disk D).** 7월 29일 원본 런타임 표는 754행이고 `D363=26`에서 끝난다. 패치표는 753행·575개 출력 위치로 두 바이트 줄여 `D361=26`으로 옮겼으며 `D362–D363=00 00`으로 마무리한다. 원문 576개 위치 중 두 `・`는 유지한 기호여서 실제 변경 대상으로 표시된 행은 573개다. 작업표는 11블록·18구간인데 마지막 블록을 34칸이라 적은 반면 하위 구간 합계는 33칸이다. `ヴ→가` 단독 시험은 raw `0x5A9E–0x5A9F`에서 표시 성공을 확인했지만, 이는 한 글자 시험이며 전체 Act 2 결과의 실행 확인은 아니다. 9월 저장 참고판은 754행·576위치·`D363=26`이다.

**Act 3 (Disk D).** 8월 1일 원본 런타임 분석은 1,948행, 본류 `D501–E208`, 종료 `E208=26`을 기록한다. 7월 31일 번역표는 23블록·51구간·1,525개 원문 슬롯을 가진다. 8월 1일 패치판은 1,915행(본류 1,637·서브스트림 278), 1,494개 번역 위치, 종료 `E1C6=26`으로 정리됐다. 뒤의 `E1C7–E208`은 미사용 영역이라는 이유만으로 새 문장을 넣을 여유 공간이 되지 않는다. 원본 실행에서 `D9BC–D9BD=22 0E`, `D9BE/D9C0=81 49`를 확인해 `0782–0784` 행의 느낌표 두 개를 분리했다. 패치 슬롯 표기는 1,493행에만 있고 26·576·668·700·730·742·773은 빠지며, 593은 세 번, 673·701·771·830은 두 번 나타난다. 따라서 번호만으로 모든 번역 행을 원본 실행 행에 대응시킬 수 없다. 9월 저장 참고판은 1,926행(본류 1,648·서브스트림 278)이며, 전체 행 대응표는 확인되지 않는다.

**Act 4 (Disk E).** 8월 1–2일 원본 런타임 표는 2,483행(본류 2,002·서브스트림 481), 1,676개 문자 위치, 3,914바이트 본류와 `E78D=26`을 기록한다. 8월 4일 교정판은 194행을 빼고 192행을 넣어 2,481행(본류 2,000·서브스트림 481), 1,674개 번역 위치, 3,910바이트, `E789=26`으로 바꿨으며 `E78A–E78D=00`을 둔다. 블록별로 2번은 57→47, 17번은 39→50, 11번은 106→115로 재배분됐다. 원시 덤프는 `E129=95 CF`를 変, `E12B=89 BB`를 化, `E12D=82 CD`를 は로 확인한다. 워크북 17번의 `変下`·`89 BA=下` 표기는 덤프와 맞지 않는 전사 오류이며, “번역란 비움”이라는 서문과 달리 표 안에는 한국어 문안이 있다. 8월 4일 교정은 정적 대조이며 그 판본의 QUASI88 실행 확인은 포함하지 않는다. 9월 저장 참고판은 원본 수치인 2,483행·3,914바이트·`E78D=26`을 보이지만 교정판과 행 단위 대응표나 원복 사유는 확인되지 않는다.

**Act 5 (Disk F).** 8월 5일 원본 런타임 분석은 서로 떨어진 두 페이로드 `DB8D–E3AB` 2,079바이트와 `D762–DCB6` 1,365바이트를 구분한다. `E3A7–E3AB=00 04 02 05 08`은 전환·로드 제어다. 2,547행 원본 실행표에서 8월 6일 패치판은 문자 행 148개를 빼고 131개를 넣어 2,530행(본류 1,701·서브스트림 829)으로 바뀌었다. 원문 1,377개 슬롯은 출력 1,360개로 줄었고, 한글 909·공백 234·문장부호 217개로 나뉜다. 첫 페이로드는 2,073/2,079바이트를 사용해 6바이트가 남고, 둘째는 1,337/1,365바이트를 사용해 28바이트가 남는다. 두 공간의 여유를 합쳐 배정할 수 없다. 편집 길이에 맞춰 전환 바이트 `E3A7–E3AB`도 `E3A1–E3A5`로 이동한다. 원본 런타임에서 직접 실행된 마지막 행은 2,536번(`DCA1–DCA2=92 85`)이며 2,537–2,547번은 정적 덤프에서 읽은 행이다. 패치 슬롯 표기는 1,357행에만 있고 369·599·823은 빠지며 366·598·821은 중복된다. 번역 작업표 52블록과 패치판 56그룹의 전체 대응표는 없다. 9월 저장 참고판은 2,532행(본류 1,703·서브스트림 829), 1,362위치다. 둘째 페이로드가 8월판보다 4바이트 늘었지만 행 단위 대응 원인은 확정되지 않는다.

Act 2–5에는 각각 원본 런타임 분석, 번역표, 패치표가 있다. 최종 D88이 확인되지 않는 범위는 특정 이미지의 재현·실행 성공을 입증할 수 없다는 뜻이며, 번역·패치 분석이 없었다는 뜻은 아니다. 완료 선언, 정적 바이트 대조, 게임 실행 확인은 확인된 범위 그대로 구분한다.

### 3.4. Disk A 엔딩과 엔딩 크레딧

8월 7일 엔딩 실행 분석은 원본 엔딩 본류 `D149–D891`의 1,865바이트를 기록한다. 실행 순서 1,132항목은 본류 934행과 삽입된 서브스트림 198행이다. `D891=26`이 종료이고 `D892` 뒤는 범위 밖이다. D88의 세 데이터 조각은 `D149–D3FF` 695바이트→raw `AF69–B21F`, `D400–D7FF` 1,024바이트→`B230–B62F`, `D800–D891` 146바이트→`B640–B6D1`이다. 사이의 `B220–B22F`, `B630–B63F` 섹터 헤더는 기록 대상이 아니다. `2D FF`에서 `CA23`에 FF를 쓰는 사실은 확인됐지만 FF의 상위 의미는 원문이 미확정으로 남긴다. 중첩 서브스트림과 덤프 전개 행은 원본 런타임 확인 행과 섞여 있으므로 각 행의 확인 방식에 따른다. 신규 확인 문자 12개의 ROM 접근값도 원본 실행 근거이지 한글 패치 표시 성공 근거는 아니다.

8월 8일 번역 워크북은 본류의 15개 call 그룹, 840개 문자 위치를 번역 단위로 재배열하고 전각 공백 `81 40`을 `␠`로 표시한다. 화자 ID는 확정하지 않는다. 서문은 번역란 공란이라고 하지만 그룹 표에는 이미 한국어 문장이 있다. 따라서 내용은 **한국어 문안이 존재하는 번역 작업표**로 읽는다. 같은 날 한글 패치표는 840개 편집 위치를 한글 547, 전각 공백 155, 문장부호 132, 특수 6으로 나누며 원본/패치 바이트·ROM·가나다 번호·raw 주소를 실었다. 실행순서에는 제어행과 서브스트림도 들어 있다. 표에 기록된 수정 700행·실제 변경 바이트 699개·삽입 78행은 저장 당시의 정적 편집 수치다. 이 기록에는 한글 엔딩의 사용자 런타임 로그가 없지만, 같은 날 사용자는 엔딩 본문 완료를 선언했고 뒤에 저장된 판본도 확인됐다. 선언·표·후속 저장판의 증거 범위는 각각 다르다.

패치표의 `패치 슬롯` 번호는 안전한 단독 식별자가 아니다. 항목 #93(`D1FA`, 냐)과 #94(`D1FC`, 느낌표)가 모두 0070이고 0072가 누락돼 있으며, #127·#128은 0105를 공유한다. #1123과 #1126에도 0836 중복이 있다. 서로 다른 실행 순번·주소·바이트이므로 같은 실제 바이트로 합쳐서는 안 된다. 런타임표 #721의 `D983=17` 복귀는 패치표 #734의 같은 주소·바이트와 대응하고, 다음 본류 `D606=41`은 패치표 #735의 `D620=41`과 대응한다. 이에 앞서 런타임표 #706–708은 `D603–D605=16 60 D9` 호출→D960→`D965=16 84 DA` 호출이고, 패치표 #719–721은 대응하는 `D61D–D61F` 호출→D960→같은 `D965` 호출이다. 뒤 본류 주소 `D606→D620`의 +0x1A 이동과 행번호 `#722→#735`의 +13은 패치 스트림 재배치와 일치해 이 순번 차이 자체는 설명된다. 다만 시작부 D601–D61A의 패치표 13개 2바이트 문자행(첫 `83 94`)은 런타임표의 같은 D601–D602 `61 62` 제어행과 충돌한다. 이 13행의 source 바이트/삽입 근거는 아직 미확정이므로, #721↔#734 및 #722↔#735의 주소 대응과 D601 충돌 원인은 분리해 둔다. 대조 키는 슬롯 라벨 하나가 아니라 실행 순번, 주소, 원본·결과 바이트와 호출 관계를 함께 써야 한다.

8월 8일 크레딧 분석·번역표는 엔딩 `D891=26` 뒤의 **별도** 크레딧 단계다. 로더·동기 경로 `C0CE→085B→0E00→C11D→C1D7`, `C22F→CC09→D8BE`, `D8CF–D9CE` 256바이트의 `1900–19FF` 이동과 `081E→0B65` 호출을 기록한다. 텍스트 스트림은 `C9C8–D2EF`, 2,344바이트이며 원본 `D2EF=FF`로 끝난다. D88 raw는 `C9C8–CBFF→9B98–9DCF` 568바이트, `CC00–CFFF→9DE0–A1DF` 1,024바이트, `D000–D2EF→A1F0–A4DF` 752바이트로 세 조각이다. 표의 그래픽 압축 파서는 텍스트 스트림과 별개다. `0D`, `00`, `01 N M`, `02 XX`, `FF`의 제어 의미를 나눠 적었고, 26개 워크시트 그룹에 한국어 문장은 이미 존재한다. 이 **분석·작업표의 상태 표기**에는 바이트 패치/런타임이 미완료로 남아 있으나, 후속 실행 보고에는 2,267바이트·`FF=D2A2` 확인과 2,265바이트·`FF=D2A0` v1.7 상태, 사용자 완료 선언이 각각 기록됐다. 앞 문서의 미완료 문구를 프로젝트의 최종 상태로 채택하지 않는다. 크레딧 화자 ID와 Disk G 일치 payload의 정확한 복사원은 원문상 미확정이다.

### 3.5. Disk G 음악 모드·경고문·당첨 알림

8월 10일 음악 모드 분석은 33곡×12바이트 record(`C64C–C7D7`), 종료/포인터 36바이트(`C7D8–C7FB`), 제목 `C7FC–CB2F`, 작곡자 `CB30–CB50`을 구분한다. 제목은 `[작곡자 인덱스 1바이트][Shift-JIS 제목][00]`이며 포인터는 record 시작 다음 바이트를 가리킨다. 원본 `作曲` 데이터 `CB51–CB55`와 `Ｄｉｓｋ` `CB56–CB5E`가 뒤따른다. 최종 내부 재패킹은 제목 804바이트(`C7FC–CB1F`), 작곡자 47바이트(`CB20–CB4E`), 새 00 두 바이트(`CB4F–CB50`)다. 제목 포인터 33개와 작곡자 포인터 `CB20/CB2F/CB3C`를 다시 계산했고, `C118`의 `CALL` 세 바이트를 00으로 바꿔 `作曲` 출력만 막으며 `C12F`의 DE 참조를 `D41A→D414`로 옮겼다. `作曲` 데이터 자체는 보존한다. D88은 `C7FC–C7FF→0x301C–0x301F`, `C800–CB50→0x3030–0x3380`처럼 raw `0x3020–0x302F` 섹터 헤더를 건너뛴다. 제목·작곡자 표시에 대해 사용자 QUASI88 성공이 기록돼 있다. 12바이트 record의 +02~+0B 의미와 반복 복사본 기능은 문서가 미분석으로 남겼다.

8월 9일 E000 시험은 서로 다른 세 관측으로 나뉜다. 15:33에는 음악 로드 뒤 E000 값이 같았고, 16:46에는 8-sector 적재 중 `00 FF…`가 보였지만 실제 write PC와 명령은 추적되지 않았다. 별도의 1-sector `39/1/5→E000` 시험은 `4001` 스텁과 `C01E` 호출로 `4F05→E000`을 확인했으나 실패 경로 `01ED`는 실행하지 않았고, `0167` 경로는 기존 검사와 충돌해 폐기했다. 이 외부 적재 시험은 최종 음악 텍스트 패치와 별개다.

두 DISK 경고문은 RAM/raw 주소와 형식이 다른 블록이다. `0/0/8`은 RAM `065F–06E3`/raw `0xA8F–0xB13` 133바이트, `39/0/5`는 RAM `0613–06B8`/raw `0x64026–0x640CB` 166바이트다. 번역 뒤 각각 129·164바이트를 쓰고 나머지는 00으로 채운다. 첫 블록은 동적 문자·드라이브 번호 이동에 따라 `0630`, `0649`의 주소 피연산자도 갱신됐다. 8월 10일 사용자 실행은 두 경고 문구의 표시 성공을 확인했지만, 당시 두 번째 블록의 동적 A 주소는 특정하지 못했다. 8월 13일 재대조는 진입 주소 RAM `0668`/raw `0x64016`, `LD (0673),A` 명령의 raw `0x64010`, 동적 A 바이트 RAM `0673`/raw `0x64086`을 연결했다. 문자열 A 영역은 이동하지 않으므로 이 주소 확인만으로 코드 피연산자를 바꿀 필요는 없다. 이 주소 분석은 8월 10일 성공 이후에 확인된 사실로 소급하지 않는다.

8월 9일 Prize 분석·번역표는 Disk G의 수평 반복 알림을 다룬다. C28/H0/R1–4의 `C000–CFFF` 4,096바이트 payload 안에서 본문은 `C6E5–CB3E` 1,114바이트다. `C6E5–CA9C`에는 2바이트 문자 476개, `CA9D=01`에는 긴 간격 제어, `CA9E–CB3D`에는 2바이트 문자 80개, `CB3E=00`에는 루프백 제어가 있다. D88 raw에서는 네 0x400바이트 섹터에 걸쳐 `477E5–478FF`와 `47910–47C4E` 두 영역으로 나뉘며 `47900–4790F` 섹터 헤더를 건너뛴다. 사용자 관찰은 오른쪽에서 왼쪽으로 반복되는 스크롤이고 시간·프레임은 측정되지 않았다. 작업표 21개 구획에는 한국어 문안이 있지만 서문과 상태란은 번역·패치 미착수라고 남아 있다. 후속 기록에는 같은 날 12:48경 사용자의 완료 선언과 9월 저장판의 551행 배치가 각각 있다. 이는 작업표의 시점 문구를 지우지도, 저장판 실행을 입증하지도 않는다. `CA9D=01`과 `CB3E=00`은 고정 제어이므로 길이 조정은 일반 문자 위치에서 해야 한다.

### 3.6. Disk A 프롤로그·메뉴, 공통 KANJI1, 게임 설명서

6월 1일 메뉴·오프닝 조사 기록은 `C227→HL=C305→CALL C588` 메뉴 문자열 출력 경로와 `C300` 메뉴, `06xx` 저주소 디스크 경고, `C8B6` 로딩 표기, Disk G PCM 47회 선적재, PCM ON 자막·음성·얼굴, `DD69` 뒤 Disk B 전환을 서로 다른 단계로 기록한다. 당시에는 PCM OFF 토큰의 검증·적용이 미완료였다. 7월 27일 Disk A UI 번역표는 C300 메뉴 17항목, 저주소 3항목, 로딩 3항목의 원시 위치와 편집 바이트를 적는다. 메뉴 17항목 중 번역·재인코딩이 채워진 것은 처음 6개이고 나머지는 원문 유지다. 메뉴 범위 `C2F6–C40B`는 D88 raw `16B6–17DB`에 대응한다. 끝 항목 `C3FE–C40B`는 raw `17BE–17BF`와 `17D0–17DB`로 갈라져 중간의 섹터 헤더 `17C0–17CF`를 건너뛴다. RAM 주소가 이어져도 raw 바이트는 이어지지 않는 사례다. 로딩 숫자 영역은 `C8B6–C8C9` 20바이트, 문자열은 `C8CA–C8D3` 10바이트다. 원문 표는 뒤 raw `1CB4–1CB6=00 00 00` 및 RAM 경계 `C8D4 또는 C8D5 확인 필요`를 적고, 요약 구간도 `C8B6–C8D5`로 잡아 경계가 한 바이트 모호하다. 그러므로 `C8D4`를 확정 종료 주소로 취급하지 않는다. A/1 고정 문구와 실행 중 G/2 같은 동적 표시를 나누고, 공란 번역행은 적용 대상으로 억지로 세지 않는다.

6월 8일 자막 HL/BC 후크 기록은 세 번 처리하는 `counter=03`과 `DAEE/DAF0/DAF2` 포인터 단계다. 6월 19일 재빌드 기록과 368개 직접 변경 구간의 판본은 문제 위치 `DB0A/DB0C` 두 번, `counter=02`, `C16A→D960` PCM 분기를 사용한다. 이 판본의 D88·ROM 원본/결과 해시, 변경 구간, 사용자 성공 확인은 그 날짜의 PCM ON 자막 표시와 PCM OFF 동작 복원, #202/203 `앗！` 표시를 가리킨다. 그때 “입 동작 억제/복구”라는 표현은 해당 판본의 보고 용어이며 `CA25` 얼굴 애니메이션 차단을 검증한 뜻으로 확정하지 않는다. 변경 구간에는 UI, `C16A/C16E/0845`, `D900/D950`, `A420/D960`, 오프닝 스트림, ROM 글리프 바이트가 함께 있다. 7월 27일에는 공용 A420 효과음 회귀 때문에 A420 전체를 RET로 유지하지 않고 호출 위치의 조건 분기로 바꾸는 후속 판본이 기록된다. 8월 14일 TEST9는 공용 코드의 **D88 원본 유지·RAM 일회 활성화/복구**로 다시 바뀌므로 6월 19일 완료 D88을 TEST9 결과라고 부르지 않는다.

오프닝 원본 payload 자료는 `D974–DD69` 1,014바이트 세트와 `D974–DDF5` 1,154바이트 확장 세트로 구분한다. 앞 세트의 `D974–DBFF` 652바이트는 raw `0x08B04–0x08D8F`, `DC00–DD69` 362바이트는 raw `0x08DA0–0x08F09`이고, 사이 `0x08D90–0x08D9F`는 섹터 헤더 16바이트다. `D982–DD68`은 999바이트인 반면 `D982–DD69`는 1,000바이트다. `DD68=26` 종료와 `DD69=09` 뒤 영역의 차이를 보존한다. 7월 27일 통합 검증표의 545항목은 한글 재인코딩 바이트와 이전 일본어 버전의 DE/ROM 런타임 로그를 한 행에서 비교하는 자료이고, 8월 14일 런타임 분석의 552항목은 원본 실행 경로의 다른 기준이다. 545행을 552행 중 7개가 검증되지 않았다는 식으로 단순 차감하지 않는다.

7월 27일 검증표의 끝 #545는 `DD68=26`이며 제공 6월 19일 D88 raw `0x08F08`도 26, 바로 뒤 `0x08F09`는 09다. 데이터 두 조각 638+361=999바이트를 읽을 때 섹터 헤더를 건너야 한다. 같은 자료의 `D974–D981` 14바이트 주장은 6월 19일 실물에서 `D974–D97F`가 후크 코드 말미와 겹치고 `D980–D981`만 00인 것과 함께 판본별로 보아야 한다. 원본 토큰열은 D974부터 시작하지만, 6월 19일 재빌드의 이벤트 본류는 D982부터 시작하며, 문서의 후크 공간 표기는 별도의 배치 상태를 가리킨다. `D974–D983`을 여유로 보면 `D982` 본류 2바이트를 포함하므로 불가하다. 삭제 후보 raw 구간은 `DD09–DD1C` 20바이트, `DD1E–DD1F` 2바이트, `DD21–DD28` 8바이트, `DD46–DD59` 20바이트로 합계 50바이트다. 따라서 “25개 2바이트 행 삭제=48바이트”와 후보 구간 합계가 다르며, 실제 삭제 로그의 길이는 별도 증명이 필요하다. 표제의 544/545 항목도 본문 표 #545와 다르다. 최신 한글 바이트 열과 옛 일본어 DE/ROM 로그를 섞어 모든 한글 글리프가 각 행에서 런타임으로 다시 확인됐다고 읽지 않는다. 8월 14일 상세 서술 역시 1~552 기본 표와 뒤의 역순 보충 블록에서 제목/주소를 잘못 재사용한 부분이 있어 실제 토큰 주소와 최종 HL을 우선한다.

6월 19일 KANJI1 배정판은 131,072바이트 ROM에 123개 글리프를 배치했다. 토큰에서 분리한 두 JIS 바이트를 `d,e`라 할 때, `d<0x30`이면 `bank=((e>>1)&0x30)`, 아니면 `bank=((e<<1)&0xC0)`을 쓴다. 이어 `hi=(((d<<1)|((e>>4)&1))&0x3F)|bank`, `lo=(e<<4)&0xF0`로 `0AEE` 접근값을 만든다. 예를 들어 `6F 5E→9F E0`이며 ROM의 글리프 시작 위치는 이 접근값의 2배, 글리프 크기는 32바이트다. 초기 배정에서 `안`은 72번째 항목(`82 E6`, 접근값 `3880`, ROM 위치 `0x07100`)이고, 기존 51개 토큰 재배정과 함께 52개 항목에 영향을 줬다. 83번째는 `82 F1`, 한자 영역의 첫 항목은 84번째 `88 9F`다. 배정표의 ROM 위치는 영역 사이를 건너뛰므로 한글 순서와 ROM 위치 순서는 같지 않다. 7월 14일의 361글리프 배정은 6월판과 10,110바이트가 달랐고, 이후 558글리프 기준은 또 다른 판본이다. 이 바이트 대조는 각 글리프가 화면에 표시됐다는 런타임 확인과 별개다.

현재 빌드는 원본 KANJI1 ROM(SHA-256 `7608040cffb1951e5cc567abb63f75b5746777a1ba96196c1b75606b793bb4bb`)에 최종 `hangul.csv`와 동일한 558행을 적용한다. 생성 ROM의 SHA-256은 `e5646601d83fc2685340a183fa50d3c4fca8daf449acefc35544ef790e775aab`다. 원본 대비 변경 16,820바이트는 모두 이 558개 글리프 슬롯 안에 있으며, 나머지 ROM 바이트는 원본과 일치한다.

게임 설명서는 28쪽이며, 한국어로 옮긴 4–9쪽에는 부팅·조작·게임 시스템이 정리돼 있다. p.4의 PC-88/98 Disk A=drive 1, Disk B=drive 2, Sound Board II 사용 시 지시에 따라 Disk G 삽입이라는 설명은 오프닝 뒤 Disk B/G 메뉴 로그의 사용자 안내 맥락을 해석하는 데 쓴다. p.5 F5 음악 모드, p.6 여섯 스테이지와 HUD, p.7 장비·HP·주얼, p.8–9 아이템 유형 설명은 게임 사용법이다. 설명서 번역을 D88 코드 경로나 패치 실행 성공의 직접 증거로 사용하지 않는다.

### 3.7. 타이틀·전투 CG 자원의 저장 경계와 확인 기록

타이틀 CG 자료를 대조하면 Disk A 로고는 네 자원으로 나뉜다. `ヴァリス`는 376×91, 3면 압축 자원(상한 `0x1346`), `II`는 152×79의 3면 비압축 interleave, `夢幻戰士`는 RAM `1908–1EF7`의 352×17 3면 압축 자원(상한 `0x05F0`), 스크롤 글씨는 RAM `1EF8–21B7`의 352×16 1bpp 자원이다. 이들은 하나의 그림처럼 보이더라도 저장 방식과 크기 경계가 다르다.

이 네 자원은 별도 파일처럼 연속 저장되는 것이 아니라 Disk A의 12개 섹터에서 RAM `1900–48FF`로 적재된다. `D3FB–D404`의 요청은 `DE=2801, BC=0C00, HL=1900`이고, RAM 포인터는 `[1900]=0008`, `[1902]=05F8`, `[1904]=08B8`, `[1906]=1A4F`라 각각 `1908`, `1EF8`, `21B8`, `334F`의 그림 경계를 가리킨다. 각 섹터는 0x400 data byte와 0x10 D88 header로 나뉘므로 12개 data 범위가 raw 파일에서 연속하지 않는다. sector별 RAM과 D88 data 주소는 다음과 같다.

변경된 `ヴァリス` 그림에 한하여 중앙 행 45/46의 애니메이션 겹침을 막으려고 Disk A `D473–D475`의 `CD 19 87` (`CALL 8719`)을 `00 00 00`으로 바꾸는 조건부 보정을 문서화한다(D88 raw `0x85F3–0x85F5`). 해당 수정에 대해서는 QUASI88 타이틀 실행 성공이 기록돼 있다. 이는 해당 보정과 테스트 범위의 기록이며 네 타이틀 자원과 전투 CG의 모든 변형 조합에 대한 포괄 검증을 뜻하지 않는다.

보정의 이유는 앞선 `D467` 중심 바깥쪽 전개가 위쪽 45행과 아래쪽 45행을 이동시키고 중앙 원본행을 Y99/Y100에 넣은 뒤, `D473`의 `CALL 8719`가 가운데 행 45/46을 서로 바꾸기 때문이다. 한글 `바리스` 그림은 이미 정상 행순서여서 그 호출만 생략한다. 뒤의 `D47A–D48C`는 `49×92` 영역을 Y=54에 고정해 8픽셀씩 왼쪽으로 일곱 번 이동시키므로 그대로 유지한다. 따라서 세 바이트 NOP은 이 중앙행 순서 문제만 해결하며 그림 자원의 전체 디코더나 스크롤 이동을 대체하지 않는다. 기록된 성공 범위도 한글 바리스 타이틀 시험 D88의 QUASI88 확인으로 제한한다.

## 4. 교차 분석: 실행 흐름, 패치 의존성, 최종 빌드

### 4.1. 게임 실행 경로와 번역 자료가 만나는 지점

부팅에서 대사 출력까지는 디스크의 선형 바이트를 그대로 화면에 찍는 흐름이 아니다. Disk A의 부트 코드가 `F000`에서 로더를 실행하고, 로더가 `3000` 영역의 실행 코드로 이동한 다음 C000 초기화 경로를 거쳐 `C01A`의 이벤트 처리기로 들어간다. 원본 이벤트 자료는 `D974`에서 시작한다고 기록되지만 6/19 rebuild는 이 앞에 hook code를 배치해 이벤트 시작점을 `D982`로 옮겼다. 따라서 `D974`라는 주소만 보고 모든 빌드의 같은 토큰을 가리킨다고 볼 수 없다(§3.6 판본별 바이트 대조). 문자 토큰은 `C671` 계열 처리에서 제어·문자 분기를 거쳐 `0AEE`의 JIS→KANJI 접근값과 ROM glyph offset으로 이어진다. 이 변환은 예를 들어 `6F 5E→9F E0`이며 offset은 접근값×2, glyph 크기는 32바이트다. `16`·`17`은 일반 표시 문자가 아니라 서브스트림 호출·복귀로 나타나며, 같은 HL에서 반복 관측된 `C604`는 대기일 수 있으므로 토큰을 소비했다고 세지 않는다. 완료 여부는 다음 포인터가 실제로 이동하는지, 출력은 화면에서 사용자가 글자를 식별했는지를 각각 봐야 한다.

이 해석은 6월 초의 토큰 #1–552 조사와 이후 한글 재배치표를 이어주는 기준이다. 런타임 표는 원본 일본어 스트림의 실행·반환 주소를 추적하고, 번역표는 그 문자 위치에 다른 바이트를 놓는 설계다. 그래서 원본의 실행 행수, 번역표의 문자 슬롯 수, 패치표의 실제 변경 행수는 서로 다른 수치다. 예를 들어 제어행·반복 호출은 실행 행에 들어가도 번역 슬롯은 아니며, 기존 기호를 보존한 편집 위치는 번역 위치 총계에는 포함돼도 바뀐 바이트 수에는 들어가지 않을 수 있다.

PCM 처리도 대사 출력과 별도 장치가 아니다. `A420`은 공통 효과음 경로이고 `C692→A420/B0EA`는 일반 문자 처리에서 발생하는 효과음 호출이다. `CA25`는 얼굴/표정 애니메이션 슬롯이며 입 전용이라고 확정할 수 없다. 6월 19일 기록의 “입 동작 억제”는 당시 사용자 확인을 적은 표현으로 보존하지만 눈에 보이는 애니메이션을 막았다는 증거로 확대하지 않는다. A420 전체를 RET로 대체하면 PCM을 끄는 대신 메뉴 효과음까지 차단했다. 이후 설계는 PCM 상태(`0017H`)를 읽는 call-site에서 효과음 처리를 분기하고 PCM OFF에서는 원래 경로를 복원하는 방식으로 좁혀졌다. 이 방향은 6/19 통합 rebuild, 7/27 call-site 수정, 8/14 TEST9에서 코드 수명 문제가 생길 때마다 달라진다. 공용 로더의 코드를 디스크에서 바꾸면 엔딩에서 같은 로더 블록이 다시 적재될 때 후크가 재등장할 수 있어, TEST9는 D88 공용 코드를 원본값으로 유지하고 프롤로그 진입 때 RAM에서만 한 번 활성화한다.

Disk 교체 오류 화면 역시 대사 디스크의 단순 자막이 아니다. `06xx` 상주 RAM의 오류 출력기와 동적 디스크 문자·드라이브 숫자 store가 화면을 만든다. 같은 문구가 Disk A 저주소, Disk B/C의 `0A80–0B04`, Disk F의 `0A3B–0AE0`, Disk G에 각기 다른 형식으로 복사돼 있다. 문장이 짧아져 동적 번호 주소가 이동하면 문자열 바이트뿐 아니라 `LD (nn),A`의 주소 피연산자나 호출 포인터도 함께 갱신해야 한다. 이 때문에 B와 C는 번호 store 이동이 일치해도 각 disk의 독립 범위를 사용하고, F의 `２`처럼 겉으로 숫자처럼 보이는 고정 문자는 동적 슬롯과 분리한다. ### 4.2. 실행·주소·자원 분석에서 확인된 관계

#### 4.2.1. 화면에 보이는 문자열과 실제 실행 경로

Disk A 메뉴의 그래픽 주소와 문자열 출력 주소는 서로 다르다. 실행 흐름 C09D→F000→F014→3000→30A3→C000→C01A에서 C227은 HL=C305를 준비해 C588 문자열 출력 경로로 넘긴다. 화면에서 그래픽으로 보였던 1Axx/1Bxx는 문자열 주소가 아니며, C305 문자 RAM과 raw 0x16C6을 각각 변경해 반응을 확인했다. #### 4.2.2. 주소 이동과 문자열 길이는 영역별로 검증한다

오프닝 본문을 2바이트 이동하고 #548 뒤 81 40 한 개를 넣은 시험은 시작 메뉴까지 확인됐다. 본문 178바이트 전체를 앞당기고 남은 곳을 00으로 채운 시험은 로고 뒤 Disk B 로드에서 멈췄다. 앞 결과는 한 토큰의 2바이트 이동만 입증한다. 전체 구간 재배치에는 적용되지 않는다. 특정 세 글자의 화면 위치를 수동 레지스터 보정으로 맞춘 기록과 후속 원복 보고도 각각 그 시험 범위만 설명한다.

#### 4.2.3. PCM 자막과 효과음은 공용 호출점을 공유한다

C16E=C8→C9 변경은 PCM ON 자막 경로의 메모리 시험이었다. A420을 RET로 바꾼 시험은 해당 호출이 있음을 보여줬지만 PCM OFF 효과음이 살아남는다는 증거는 아니었다. 최종 ON/OFF 분기는 토큰 28 시점 C16A→D960이 0017H를 확인해 A420을 ON에서 C9, OFF에서 C3 EA B0으로 설정한다. 두 모드에서 시작 메뉴까지 진행한 사용자 확인이 기록돼 있다. 느낌표 보정도 처음의 DB08/DB0A 조건으로는 두 번째 행을 놓쳐, D900 진입 진행 포인터 DB0A/DB0C를 사용하고 비교 카운터를 03→02로 바꾼 뒤 앗！ 표시를 확인했다.

이후 효과음 소실 보고로 공용 A420 상태가 다시 검토됐다. QUASI88 덤프 A420=C9 EA B0에서 첫 바이트를 C3으로 복원하자 소리가 돌아왔다. 후속 패치는 A420=C3 EA B0을 보존하고 C692 효과음 호출점에서 PCM 조건을 처리해 D960으로 넘긴다. 따라서 시작 메뉴까지의 ON/OFF 확인과 후속 효과음 회귀 수정은 다른 검증 항목이다.

프롤로그용 영구 hook은 후반부 Disk A 공용 코드가 재로드될 때 다시 나타나는 문제가 있었다. F140 상주 복사, 307D/3081 호출 변경, D8C2 재배치, C000 분기, DD68 포인터 PRECHECK, D931/D8C8/D900 hook을 시험했으나 엔딩 중단·CG 파손·같은 멈춤을 보고한 경로는 성공판에서 제외됐다. D8DF–D958 덮어쓰기 주장은 관측값이 없어 철회됐다. 확정 TEST9는 D88 공용 코드 0845=C3 F2 09, C692=CD 20 A4, C16E=C8을 원본으로 두고 D974=1E 6C DD에서 DD6C 일회 트리거를 실행한다. wrapper는 RAM의 세 지점을 활성화하고 DD6C 첫 3바이트를 2A 4F A4로 즉시 되돌리며, 세 처리가 끝나면 D930이 공용 RAM 지점을 원복한다. 정적 diff는 raw 0x256E 1바이트, 0x2AA3–0x2AA4 2바이트, 0x6D66–0x6D67 2바이트, 0x8A83 1바이트, 0x8A9B–0x8AD1 55바이트, 0x8F0C–0x8F0E 3바이트로 합계 64바이트다. 사용자는 해당 판본으로 프롤로그와 엔딩 통과를 확인했다.

#### 4.2.4. 글리프 ROM 시험은 문안 전체의 실행 확인과 구별한다

초기 토큰·ROM 조합에서 한글 대신 다른 글리프가 나오거나 모니터 Return에서 멈춘 사례가 있었다. #### 4.2.5. 엔딩·크레딧·Prize·음악은 각각의 고정 스트림을 가진다

엔딩 본류 D149–D891은 1,865바이트이고 실행 항목 1,132개는 본류 934행과 서브스트림 198행으로 나뉜다. D891=26이 종료다. #721/#734는 D983=17 복귀 주소와 일치하지만 #722/#735는 패치 스트림 재배치로 D606→D620에 대응한다. 패치표의 D601–D61A 13행은 원본 D601=61 62 제어행과 충돌해 별도 미해결이다. 엔딩 텍스트의 제어·복귀 주소를 단순한 문장 행으로 읽지 않는다.

크레딧은 엔딩 종료 뒤 별도 호출·스트림이다. 원문 C9C8–D2EF는 2,344바이트이고 세 D88 구간으로 나뉜다. 작업표의 26그룹에는 한국어 문안이 있으며, 서로 다른 실행 보고에는 2,267바이트·FF=D2A2와 v1.7판 2,265바이트·FF=D2A0이 나온다. 이들은 다른 payload 판본이다. Prize 본문은 1,114바이트, 한국어 문안은 21그룹으로 기록됐고 CA9D=01 및 CB3E=00은 고정 제어다. 작업표의 예전 미착수 표기와 후속 완료 선언은 서로 다른 자료 상태를 가리킨다.

음악 모드의 제목·작곡자 재패킹과 E000 외부 적재 시험도 분리한다. 최종 음악 패치에서는 포인터를 갱신하고 사용자 QUASI88 실행 성공이 기록됐다. 별도의 8-sector 적재 관찰은 E000에 00 FF…가 보였다는 사실만 남기며 실제 write PC는 찾지 못했다. 독립 1-sector 시험에서는 39/1/5→E000 로드와 4001 스텁·C01E 호출을 통해 4F05→E000을 확인했다. 실패 경로 01ED는 실행하지 않았고, 기존 검사와 충돌한 0167 경로는 채택하지 않았다. 값이 로드 전후 같다는 관측, 적재 중 메모리 스냅샷, 실제 쓰기 명령의 실행은 서로 대체할 수 없다.

#### 4.2.6. 타이틀과 전투 그림은 각각의 저장 경계에 맞춰 인코딩한다

Disk A의 타이틀은 한 덩어리 이미지가 아니다. 최종 夢幻戰士 그림은 RAM 1908–1EF7의 3-plane 압축 자원이고, 1EF8–21B7의 이동 그림은 별도 자원이다. 1EF8 자료만으로 전체 최종 로고를 설명하던 초기 해석은 실물 D88 대조 뒤 수정됐다. D473–D475의 CD 19 87→00 00 00 보정 뒤 중앙 행 표시와 타이틀 진행이 정상이라는 사용자 QUASI88 확인이 있다. Disk B 전투 CG는 640×200 3-plane의 별도 압축 자원으로 적용한다. A/B D88 간 차이 바이트 전부를 CG라고 돌리지 않고 각 선언된 원시 위치와 최종 출력의 직접 비교로 귀속한다.

## 5. 판정 기준

완료 분석은 한국어 문안, 토큰·글리프 배정, raw D88 적용, 실행 결과를 영역별 자료와 연결해 기록한다. 사용자 완료 선언과 실행표의 확인 범위는 그 자료에 적힌 행·주소·시험 대상으로 판정한다.

주소 대응은 입력 바이트, RAM 위치, D88 raw 위치, 호출·복귀 흐름을 직접 맞춘다. 같은 문구가 여러 디스크에 있어도 각 복사본 주소를 별도로 확인한다. 행 수, 문자 위치, payload 크기와 최종 원본 대비 변경 바이트는 각각 다른 집계로 제시한다. 제4.3절은 이번 최종 산출물을 일본 원본과 직접 대조한 결과다.

## 6. 통합 결론

바리스 II의 한글화 대상은 하나의 연속 텍스트가 아니다. 메뉴 문자열, 이벤트 스트림, 상주 오류 화면, 음악·당첨 데이터, KANJI1 글리프, 타이틀·전투 CG는 서로 다른 저장 위치와 출력 경로를 쓴다. 섹터를 건너는 raw 배치에는 16바이트 헤더가 끼고, 문장 길이가 바뀌면 포인터나 동적 store 주소까지 함께 이동할 수 있다.

PCM 수정은 공용 효과음 경로 전체를 바꾸면 메뉴 효과음까지 끊길 수 있음을 보여줬다. 최종 TEST9는 재적재되는 공용 디스크 코드를 수정하지 않고 프롤로그 진입 때 RAM에서 한 번 활성화한 뒤 복구한다. 타이틀 CG의 중앙 행 보정, Disk B/C 오류 문구의 동적 번호 이동, Act 5의 분리된 두 페이로드도 각각 독립 주소와 용량을 지켜야 한다.

실행 추적, 원본과 최종 빌드의 바이트 대조, 사용자가 확인한 게임 진행 기록을 영역별로 연결했다. 프롤로그와 엔딩 TEST9 진행, 효과음 회귀 수정, Disk A 타이틀 보정, Disk B 전투 CG, 각 이벤트와 고정 문구의 변경은 각 자료가 직접 다루는 주소와 범위에 따라 최종 산출물에 반영했다. 원본 대비 최종 변경 바이트와 산출물 지문은 제4.3절에 정리했다.
